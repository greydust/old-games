# 臥龍傳（WDRAGON）解包紀錄

執行 `python tools/unpack_wdragon.py`，預設讀取 `local/binary/WDRAGON/`，
輸出至 `local/extracted/WDRAGON/`。只使用 Python 標準函式庫，原始檔只讀。

目前輸出包含 69 個原檔副本、20 個 RLE 解壓檔、1,023 個非零索引對話項目，
以及 24 個索引資料區塊。`manifest.json` 記錄輸入 SHA-256、輸出路徑、長度與狀態。
上述通用解包輸出留在 Git 忽略的 `local/`。
另執行 `python tools/extract_wdragon_data.py`，可由原始檔直接重建
`assets/games/wdragon/` 的網站 JSON 與地圖 PNG，不依賴解包暫存目錄。

## 已驗證的結構

- RLE：前 4 bytes 是 little-endian 解壓長度。讀取一個 byte；若下一個
  byte 相同，消耗這個相同 byte 和後續計數 byte，輸出該值共 `count + 2` 次。
  否則只輸出該 byte。必須耗盡輸入且輸出長度完全吻合才接受。
  片頭 `OPEN_S1` 至 `OPEN_S6`、片尾 `END_S1` 至 `END_S12`、
  `GAMEOVER.DAT` 與 `MMAP.MAP` 共 20 檔通過此檢查。
- `TALK.DAT`：前 2,048 bytes 為 1,024 個 little-endian uint16 絕對位址，
  其中一個為零；其餘指向 Big5 對話資料。JSON 保留索引、位址、原始 hex，
  文字輸出把 NUL 換成換行。控制碼的完整意義尚未確認。
- `INSTALL.MAP`、`INSTALL.SCH`、`PASS.MAP`、`PASS.SCH`、
  `MOUSE.MCH`、`MOUSE.SCH` 各有 512-byte 索引區；每筆為
  little-endian uint32 位址及長度。匯出前驗證區塊在原檔範圍內。
- `.BRG` 檔案長度可按每組 48 bytes 分割，每組可分成 16 色的三分量。
  匯出原始分量，未指定 RGB 通道對應。

## 劇本、角色及據點

`SINARIO.DAT` 為四個等長 `0x56C0` bytes 劇本，標題在各劇本 `+0x40`。
程式載入劇本時的記憶體記錄位址比檔內相對位址少 `0x80`。
本文件以下程式位址均指 `KI.EXE` 去掉 `0x200` bytes MZ header 後的載入映像，
不是原檔位址。例如原檔 `0x79B6` 對應載入映像 `0x77B6`。

角色表在每劇本 `+0x42C0`，每筆 32 bytes。
127 個具名槽位後有一筆「－－－」佔位記錄，不當成角色匯出。
各劇本可能有未登場或非現役角色，不能把 127 筆都解讀成可立即指揮的武將。

| 記錄內位移 | 型別 | 欄位／證據 |
| --- | --- | --- |
| +2 | 6 bytes Big5 | 姓名，保留遊戲字形與用字 |
| +8 | 6 bytes Big5 | 另一姓名欄，目前大多與姓名相同，語意待確認 |
| +0x0E～+0x10 | byte × 3 | 高四位元依序為城塞戰、野戰、海戰適性；低四位元用途未確認 |
| +0x11 | byte | 武術，列表顯示讀取於 `0x77B6` |
| +0x12 | byte | 統率，列表顯示讀取於 `0x77C6` |
| +0x13 | byte | 政治，列表顯示讀取於 `0x77D6` |

據點表在每劇本 `+0x8C0`，192 筆，每筆 32 bytes。

| 記錄內位移 | 型別 | 顯示欄位／換算 |
| --- | --- | --- |
| +2 | 6 bytes Big5 | 據點名 |
| +8 / +0x0A | uint16 LE | 世界地圖 x / y；全部落在 384 × 256 範圍 |
| +0x0C | uint16 LE | 生產力上限；`0x56E1–0x56E9` 將新生產力截至此值 |
| +0x0E | uint16 LE | 生產力（`0x7507`） |
| +0x10 | byte | 上昇率：原值 − 100（`0x7515–0x7525`） |
| +0x11 | byte | 防災（`0x752B`） |
| +0x12 | byte | 城兵上限，與目前城兵相同採十人單位；`0x420B–0x4231` 補充後截至此值 |
| +0x13 | byte | 城兵：原值 × 10（`0x753B–0x7545`） |
| +0x19 | byte | 內政官索引；`0x74BE–0x74DC` 對應角色表，FF 無任命 |

原始 hex、絕對檔案位址及雜湊保留在 `local/extracted/WDRAGON/site-evidence.json`，不加入網站 JSON 或頁面。網站武將 ID 使用各劇本的零起始記錄索引。生產力不是 `+0x0C`；
不能僅依數值大小猜測欄位。能力名稱由原始表頭與顯示例程共同確認。

### 勢力、募集與相鄰據點的新確認

每劇本 `+0x80` 起為22個64-byte勢力槽。第一 byte ≥128者為有效勢力，
四劇本分別有22、11、6、4個。`0x7BDF–0x7C28` 依序顯示 `+1` 君主、`+2` 軍師、`+3` 首都；
君主與軍師索引到武將，127為無軍師佔位；首都索引到城池。
`+4/+6/+8` 為預備騎兵／弓兵／步兵，儲存單位為十人；
`+0x20..0x22` 為帶符號24-bit資金，`+0x18` 武將數、`+0x23` 據點數。
網站使用遊戲儲存的計數，不擅自以推算值覆蓋；第四劇本孫權的據點數55與城池歸屬計數54存在差異。
資金增額例程 `0x5609` 截至 `0x09FE98`，即655000；預備兵增額 `0x55EC` 截至65500個十人單位。

修正先前「募集設定屬各勢力獨立欄位」的表述：`0x8CAE–0x8CCE` 將劇本前0x3B bytes
載到CS:0xCF0，募集設定CS:0xD0A/0xD0C/0xD0E及下月設定CS:0xD12/0xD14/0xD16
屬於這段玩家全域標頭。`0x5410–0x541E` 只有當前玩家勢力走募集上限分支，其他勢力走AI分支。
因此不能從勢力記錄直接匯出各勢力的「募集設定」。

城池募集基值由 `0x54FC–0x55A5` 計算。設：

```
D = max(abs(城池x − 首都x), abs(城池y − 首都y))
Q = D≤80 時2、80<D≤200 時3、D>200 時4
A = floor(floor(生產力 / Q) / 32)

y<80：弓=A//32，步=A//4+A//8，騎=A−弓−步
80≤y<150：騎=弓=A//8，步=A−騎−弓
y≥150：騎=A//32，弓=A//2，步=A//2−騎
```

各結果乘10為人數。這是各城匯入勢力的基值，不是實際保證募集量；
玩家募集上限、AI財政分支及預備兵總上限都會影響結果。南部公式兩次取整保留，不能假設三者總和總等於A。

城池 `+0x1C..0x1F` 為四個相鄰據點索引，255 表示無連線。
更正：`+0` 低四位元標示的是不同勢力的連線，不能用來篩選所有相鄰據點。
`0x2CDF–0x2D33` 逐位元檢查後讀取對應據點的勢力，用於勢力鄰接計算；
完整證據見 `0x890A–0x895C`，下節另述。

內政更新 `0x4194–0x4207` 在玩家城池且內政官有非零 `+0x1A` 狀態時，
以政治加5作提升判定參數，並讀取武術作城兵補充量參數的一部分；
政治確實影響上昇率與防災更新。該狀態欄的完整語意與觸發週期仍未確認，不能宣稱永久每回合固定增長。

## 兵種與能力用途

`TALK.DAT` 對話索引 18、19、20 明確包含「騎兵／弓兵／步兵募集人數」。
輸入例程 `0x67E6–0x6845` 給三者相同的 10000 上限參數，並以整數除 10 儲存。
兵種代碼 1／2／3 已藉由編組扣除預備兵的位址確認為騎兵／弓兵／步兵，見後文。
這不代表權重表就是兵種相剋表。

原檔 `KI.EXE +0x5320`（載入映像 `0x5120`）含 4 × 4 bytes 權重表：

```
2 3 3 0
3 2 1 0
1 3 2 0
2 1 2 0
```

`0x5285–0x52D6` 以模式選列、兵種代碼減一選欄，對六個編制的數量加權，
另有能力及士氣修正。這不是最終傷害倍率；模式名稱與兵種對應仍未確認。

`0x52D7–0x533C` 同時使用武術、統率、隨機分支及適性。
`0x5309–0x5320` 取適性高四位元，計算以 `16 − 適性` 為分母的修正。
`0x55A6–0x55EB` 另計算三項適性之和加上武術、統率各兩倍，寫到角色 `+0x1F`；
該合成值用於同座標同勢力軍團的選擇評分（見下節），不標作攻擊力。
政治在 `0x3771–0x382D` 被比較及搜尋高值角色，交涉用途仍待實戰核對；
尚未確認政治對生產與防災的完整公式。

## 武將與城池剩餘欄位追查

以下位址均為 KI.EXE 去掉 0x200-byte MZ 標頭後的載入映像位址。
不能把軍團表（0x2240 起、64 bytes）與武將表（0x4240 起、32 bytes）的同名偏移混用。

### 新確認的武將欄位

自刎旗標：武將 +0 的 bit 0x10。`0x29F4–0x2A06` 在被俘處理中交換
歸屬，將原歸屬保存於 +0x1D；`0x2A08–0x2A10` 檢查原勢力有效狀態，
僅當原勢力已無效且此旗標非零，跳到 `0x2A57` 清除武將有效狀態與歸屬。
該分支無隨機判定；`0x2A6F` 的 TALK.DAT 索引67明確顯示「自刎而死」。
旗標不表示每次戰敗都自刎。網站以「自刎」是／否欄表示，提示完整觸發條件，
各劇本分開讀取。四劇本設定人數依序為27、19、18、15。

| 欄位 | 確認內容 | 程式依據 |
| --- | --- | --- |
| +0 bit 0x40 | 君主旗標；身分碼為 0 時顯示君主 | 0x7771–0x777D |
| +0x17 | 0＝－－－、1＝軍團長、2＝內政官、3＝外交官、4＝俘虜 | 0x7771–0x7795，字串表 0x75A4；0x6F3F 成立軍團時寫入 1 |
| +0x18 | 按月遞減的登用／俘虜處理等待計數；非零時不進行相關判定 | 0x586F–0x588B；0x1DC1 更新月份後經 0x5358、0x538E 呼叫 |
| +0x19 | 預定加入勢力；255 時改走隨機登用分支，也影響俘虜歸降判定 | 0x5899–0x58C2、0x594C–0x5952；不能稱為忠誠值 |
| +0x1A | 內政／外交共用的工作計數，非零才生效；不是永久能力值 | 內政 0x41B7–0x41C6、費用事件 0x573F；外交 0x3EA5–0x3EBA、0x57B8 |

| +0x1F | 三適性高四位元之和＋武術×2＋統率×2；軍團選擇評分的因子 | 0x55A6–0x55EB、0x4CAB–0x4CF2 |

俘虜處理的事件名稱由 TALK.DAT 65「俘虜的…逃走了」及 66「…已歸降我軍」交叉確認。
等待計數歸零後仍有隨機／勢力條件，不能換算成保證登場日期。
軍團選擇程式從同座標、同勢力的候選軍團中，選取
`(軍團word+4 >> 4) × (軍團byte+6 >> 4) × ((武將+0x1F >> 4)+1)` 最大者。
軍團兩欄的完整語意仍未在此證明，因此不將合成值命名為「攻擊力」。

### 三項適性的作戰模式對應

已確認高四位元的用途依序為據點戰／陸戰／海戰，原作武將自述的稱呼則是
**城塞戰／野戰／海戰**，不是騎／弓／步適性。網站使用原作自述稱呼加上「適性」作欄名；
尚未發現遊戲介面將這三項數值列作表頭，因此不將完整欄名字串冒充原始表頭。

名稱的直接映射證據：`0x638F–0x63B9` 比較武將 +0x0E、+0x0F、+0x10 的整個 byte，
取最大者（同值時依前欄優先），分別選邏輯對話 0x1A9、0x1AA、0x1AB。
`0x763–0x778` 將邏輯對話展開為 `(ID−406)×8＋武將+0x1E＋406`。
三組實際 TALK.DAT 索引依序為 558–565、566–573、574–581，每組八種口吻：

- 558：「我嗎？我最擅長城塞戰了。」
- 565：「城塞戰，我對防守比進攻更加熟練。」
- 566：「野戰的話，就由我出陣吧！」
- 574：「我擅長於海戰！」

因此遊戲文字、三欄排序、戰鬥模式選取三者互相吻合。此比較直接使用整個 byte，
雖然高四位元決定主要大小，低四位元也可能打破高四位元相同時的排序；
這只證明低四位元會影響自述選擇，尚不足以推定其獨立能力意義。

完整呼叫鏈：

1. 據點交戰 `0x4AF3–0x4B03` 保存城池指標至 CS:0xD32，
   將城池索引（0..191）存入 CS:0xD34。
2. 戰術初始化 `0x9A5E–0x9A6F` 將 CS:0xD34 分為三組：
   `<0xC0` → 模式 0、`0xC0..0xD0` → 模式 1、`>=0xD1` → 模式 2，存入 CS:0xD34B。
3. 畫面 `0xC978–0xC999` 在模式 0 顯示城池名稱；模式 1/2 分別取
   CS:0xD45E 的六位元組字串「陸上　」與「海上　」。此為名稱映射的直接證據。
4. `0x9C13–0x9C40` 取軍團主將的武術、統率，再讀取武將
   `+(0x0E + CS:0xD34B)`，右移四次，得到適性。
5. `0x9B40–0x9B4B` 以 `(2×武術＋適性)×2` 建立一項戰術參數；
   `0x9B79–0x9B89` 另將適性加到統率後建立部隊參數。
   因此三欄不只是圖像代碼，而是實際參與能力計算。

據點戰同時包含攻守雙方：`0x9B28–0x9B36` 對雙方各呼叫一次參數建立，
且共用同一個作戰模式。因此第一項不能只叫「攻城」而排除守城。
自動結算也交叉吻合：`0x4ED7` 的據點交戰傳入模式 0，
`0x4E5C` 的軍團交戰傳入模式 1，再由 `0x5309–0x5310` 取對應適性。
自動軍團交戰固定取第二項，沒有另選海戰項的分支；海戰項的已確認使用處為戰術戰鬥。

驗證：執行 `python tools/verify_wdragon_proficiencies.py`，
核對十一組關鍵指令、原始陸上／海上字串、三組適性自述與全部 508 筆網站適性數值。
報告保存於 `local/extracted/WDRAGON/proficiency-verification.json`。

## 武術、統率與適性公式核對

設 W＝武術、L＝統率、S＝當次作戰適性。以下是已確認的中間參數，
不可把它們直接命名為最終傷害／傷亡公式。

### 戰術戰鬥

`0x9C13` 返回 DL=W、DH=L、CH=S。`0x9B43–0x9B4B` 對雙方武將建立：

```
武將戰術能力基值 = (2W + S) × 2 = 4W + 2S
```

`0x9B79–0x9B90` 對編制建立：

```
部隊戰術能力基值 = floor((3 × (L + S) + T) / 4)
T = 兵種代碼1時30、2時4、3時12
```

補正表來自載入映像 0x9C0F 的三個 bytes；代碼1＝騎兵、2＝弓兵、3＝步兵。
因此公式補正為騎兵30、弓兵4、步兵12。

兵種名稱交叉確認鏈：

1. TALK.DAT 索引18／19／20分別為騎兵／弓兵／步兵募集輸入；
   `0x67E6–0x6841` 將結果依序寫入下月 CS:0xD12／0xD14／0xD16。
2. 月更新 `0x53A6` 起將下月設定移至本月，`0x54C1–0x54D9` 依序將三種募集上限
   套用於堆疊募集量 +4／+6／+8，`0x5421–0x5442` 再依序加入勢力 +4／+6／+8。
3. 編組 `0x6CA7–0x6CB3` 將 DI 指向所屬勢力 +4。
   `0x46D4–0x46FF` 取編制兵種代碼k，讀取並扣除 `DI + 2*(k-1)` 的預備兵，
   將分配量寫入編制 +1。因此代碼1、2、3各自直接使用騎、弓、步預備兵。
4. 戰術參數建立 `0x9B76` 讀取相同編制的兵種代碼，
   `0x9B7E–0x9B89` 用 k-1 索引30／4／12補正表，並無中途重新編碼。

此處使用 byte 運算，但四初始劇本的 W/L=1..15、S=0..10 不會造成這兩式溢位。
後面的 `0x9B9E` 比較的是已乘18的兵種代碼與1，不能直接把該分支解釋為
「兵種1陸戰加倍／海戰減弱」；在代碼1..3時此條件不成立。

武將能力基值在 `0xA364–0xA36E` 與戰術武將的 +3 相乘後參與雙方判定；
部隊能力基值在 `0xB61F`、`0xB6D9–0xB6EA`、`0xB703–0xB712`
參與隨機判定、能力差截斷及對目標 +3 的扣減。+3 的完整遊戲語意與
各分支的動作名稱未全部核對，因此網站只稱戰術能力基值，不稱攻擊力或傷亡。

### 自動結算

`0x52E7–0x5304` 的分支必須保留，不能簡化成固定取武術或統率最大值：

```
W >= L：
  隨機值 & 3 != 0：C = 2W
  隨機值 & 3 == 0：C = W - floor(W/4) + L
W < L：
  C = 2L - floor(L/4)

K = floor(16C / (16-S))
修正後戰力 = floor(B*K/1024) mod 65536
```

最後一式由 `0x5314–0x5337` 的除法、乘法、byte 重排及帶進位右移確認；
不能漏掉除1024，或把中間取整移到乘B之後。K 是整數，16/(16-S) 是其取整前的
適性增益；S=0、4、8、10 時分別為1、4/3、2、8/3。
例如 C=20，K 分別為20、26、40、53；不是固定每點加某個百分比。

B 由 `0x5285–0x52D0` 先以兵種權重累加六個編制數量，模式0另加據點城兵，
再乘 `floor(軍團+6 / 8)`（士氣相關欄），以16-bit結果傳入。據點戰自動結算
攻方權重選列3、守方選列0，但雙方適性都選第一項；軍團交戰選第二項，沒有海戰項分支。
後續 `0x5155–0x5178` 會為雙方修正後戰力加8，再以強弱比作截斷，
並經 `0x51B3` 的隨機編制損失與退卻等處理。因此以上尚非完整的傷亡或勝率公式。

驗證工具 `tools/verify_wdragon_combat_formulas.py` 核對原始指令、募集對話及補正表，
對 W/L=1..15、S=0..10、四個隨機分支與六種基數執行59400組比較：
逐步模擬原始暫存器運算的結果，與上述公式一致；另檢查全部戰術基值組合。
這是靜態指令與算術驗證，沒有宣稱已在遊戲執行中量測完整戰鬥結果。
報告位於 `local/extracted/WDRAGON/combat-formula-verification.json`。

## 戰術戰鬥：逐動作扣減與回寫

本節記錄已確認分支；不宣稱特殊動作、全部勝負與撤退條件均已完成。
戰術單位每筆32 bytes，CS:0xD30E為其段，兩方分別0..0x5FF、0x600..0xBFF。
+4為類型：0武將、18騎兵、36弓兵、54步兵（原兵種代碼乘18）；+0x18為戰術能力E。
+3由 `0x9B73`、`0x9BBD` 複製軍團士氣，武將則由 `0x9B54–0x9B68` 另作初始化，
故稱場上單位士氣，不將這個byte直接當兵數。低於100時另會改變動作狀態。

### 近戰對普通部隊

`0xB533–0xB5B1` 區分敵我、武將與部隊後呼叫0xB618或0xB6BC。
`0xB618–0xB6BB` 的部隊目標分支：

```
U = 隨機byte & 127
判定值 = U + 攻方E
若局勢不利：判定值 = max(0, 判定值-50)
判定值 >= 70 才成功

基本扣減 = 攻方E
若局勢有利：基本扣減 = min(255, 攻方E+64)
若攻方+0x1A==2：再加200並飽和至255
目標+3 -= 扣減，扣盡時清除有效狀態並設為0
```

局勢取CS:0xD31E：1中性，0或2與攻方陣營對照後判有利／不利。
`0xAE35–0xAE4C` 與帶+0x19非零的場上單位計數有關；這個計數的完整遊戲語意
尚未核對，因此不把局勢任意命名為地形、包圍或兵種相剋。
+0x1A==2的動作名稱也未確認，網站明示此特殊加值仍待解明。
原始四劇本E的範圍使U+E不會在byte相加時溢位。

### 近戰對武將

`0xB6BC–0xB731`：目標+3<=1或特定動作碼0/5時直接返回。
其餘情況，隨機byte R<25立即成功；否則再取U=隨機byte&127，
只有U<min(24,max(0,攻方E-守方E))成功。
成功扣max(1,floor(攻方E/8))，+3最低保留1。不能把兩次隨機合併成一次。

### 投射物碰撞

`0xAD2D` 與 `0xAD7F` 兩條生成流程分別傳入CH=28及32；
`0xB8CF` 將其保存為投射物+4，`0xB97E–0xBA2D` 在遇到有效敵方單位後扣其+3。
目標類型54（步兵）扣floor(投射物值/4)，即7或8；騎兵與弓兵扣原值28或32。
武將類型0：目標+2 bit 0（0x01）為零時忽略此命中，非零則扣floor(值/4)。
扣盡時部隊失效，武將保留1。兩種投射物的資產名稱與觸發條件未全部解明，
故不擅自命名弓箭、火箭或砲彈，也不將「碰撞後扣減」叫作射擊命中率。

### 戰後兵數與士氣

`0x9C45–0x9CAE` 投入場上單位時減少編制待投入數；
`0x9F2C–0x9F50` 逐一計數每方48個有效場上單位，依編制寫入存活計數。
`0x9F69–0x9F7B` 以「待投入數＋有效場上單位數」回寫六編制，每單位十人。
所以軍團實際損兵依有效單位是否失效而定，不等於場上+3扣減量。

`0x9EDD–0x9F23` 依CS:0xD349勝方索引0/1處理另一方：
敗方原軍團士氣>99時改為99，否則改0；勝方保留原值。
`0x9F80–0x9F98` 再按下式回寫：

```
新軍團士氣 = floor(士氣基準 × 戰後兵力 / 戰前兵力)
勝方基準=原士氣；敗方基準=原士氣>99時99，否則0
兵力為0時士氣0
```

這與自動結算的敗方100基準不同。場上士氣不逐個平均回寫。
CS:0xD349在正常戰鬥以外還有2狀態，該中止／未決狀態的完整流程仍待核對。
`0xA727–0xA746` 在一方場上單位計數為0時寫另一方勝利，但尚有武將、命令及
城塞專用分支，不能將「全軍失效」宣稱為唯一勝負條件。

驗證：`python tools/verify_wdragon_tactical.py` 核對18組原始指令及65536組扣減邊界，
報告保存在 `local/extracted/WDRAGON/tactical-verification.json`。
尚缺動作名稱映射、局勢計數完整語意、投射物種類、地形遮擋及完整勝負／退卻條件。

## 戰略地圖

`MMAP.MAP` 經 RLE 解壓後 98304 bytes，按 384 × 256 列優先排列，每 byte 是圖塊索引。
`MMAP.MDL` 為 256 個 16 × 16 圖塊，每圖塊 128 bytes：四個完整 32-byte 位平面，
每行 2 bytes，位元由 MSB 到 LSB。重建後可辨認連續河流、山脈、道路與據點圖形；
劇本城池 x/y 與世界圖塊位置一致。

網站提供保留全部原始像素的 6144 × 4096 PNG，以及 1536 × 1024 取樣預覽。
調色盤使用 `GAMEPAL.BRG` 第一組，將三分量按 1／2／0 排列作 RGB 並乘 17；
此順序依圖像顏色推定，尚未與執行中的遊戲核對，網站已標註。

## 標題畫面

`tools/export_wdragon_title.py` 從 `OPEN_S6.DAT` 匯出 `assets/games/wdragon/title.png`。
RLE 解壓後為 128000 bytes，640 × 400；上下各 200 行分別儲存四個 16000-byte 位平面。
`D7OPEN.EXE` 載入映像 `0x4CA–0x51F` 將上下半畫面各繪製一次，
第二半目標位址由 `0x4F1` 的 `mov bx,0x3E80` 指定，`0x500` 的
`mov ax,0x1005` 選擇 `OPENPAL.BRG` 第六組調色盤（零起始索引 5）。
調色例程 `0x615` 依序讀入 B/R/G，`0xAE0–0xB2F` 以 R/G/B 順序寫 VGA DAC，
因此此標題的通道排列已有程式證據。PNG 將四位元分量映射至 0–255。
